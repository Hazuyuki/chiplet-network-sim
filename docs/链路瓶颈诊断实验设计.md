# 链路瓶颈诊断实验设计

目标：在 64 卡 8 机、ring all-reduce 场景下，定位**到底卡在哪些链路上**（GPU→Leaf / Leaf→Spine / Spine→Leaf / Leaf→Leaf / Leaf→GPU）。

---

## 1. 方法一：链路阻塞计数（已实现）

### 1.1 原理

当某包本周期因「出链路已被占用」（`allocate_in_link` 返回 false）而无法发送时，记录**发送端 (node, port)**。按 NVSwitch 端口布局将 (node, port) 归类为：

- **GPU→Leaf**：GPU 的出口
- **Leaf→GPU**：Leaf 到 GPU 的端口
- **Leaf→Leaf**：Leaf 到同组其他 Leaf 的端口
- **Leaf→Spine**：Leaf 到 Spine 的上行端口
- **Spine→Leaf**：Spine 到 Leaf 的下行端口

统计各类型的「未能发送」次数；**占比最高的类型即为瓶颈段**。

### 1.2 运行方式

```bash
cd build
./test_link_bottleneck_diagnosis
```

- 输出：终端表格 + `output/link_bottleneck_by_type.csv`
- 配置：64 卡 8 机，ring_all_reduce，注入率 5（饱和点附近），warmup=500，measure=1000

### 1.3 当前结论（示例）

| 链路类型   | Blocked 占比 | 解读       |
|------------|--------------|------------|
| Leaf→GPU   | **99.9%**    | 瓶颈在此段 |
| Spine→Leaf | ~0.0%        | 非主要瓶颈 |
| Leaf→Spine | ~0.0%        | 非主要瓶颈 |
| GPU→Leaf   | ~0.0%        | 非主要瓶颈 |
| Leaf→Leaf  | 0%           | 组内非瓶颈 |

即：**交换机到 GPU 的下行链路**上，多流争用同一出端口（同一 GPU 入口），导致大量「本周期无法发送」。

## 2. 方法二：分段隔离实验（不改代码）

通过改变拓扑/参数，观察饱和吞吐变化，推断瓶颈所在段。

| 实验 | 做法 | 若瓶颈在该段则预期 |
|------|------|--------------------|
| **E1 单机 vs 多机** | 1 组 8 GPU（无 spine）ring all-reduce，测饱和吞吐 X；再 8 组 64 GPU（有 spine）测饱和 Y | 若 Y << X，则跨组（Spine）段是瓶颈 |
| **E2 减 GPU 端口** | 将 `gpu_nvlink_ports` 从 18 改为 9，其余不变，测饱和 | 若饱和明显下降，则 GPU→Leaf 是瓶颈 |
| **E3 减 spine-leaf 链路** | `spine_leaf_links_per_pair` 从 4 改为 1，测饱和 | 若饱和明显下降，则 Spine–Leaf 段是瓶颈 |
| **E4 减 Leaf 数** | `num_switches_per_group` 从 4 改为 2（每组 2 个 Leaf），测饱和 | 若饱和下降，则 Leaf 数量/组内带宽或 Leaf→GPU 争用更严重 |

### 2.1 运行示例

```bash
# E1：单机 8 GPU（无 spine）
./build/ChipletNetworkSim input/nvswitch_8gpu_single_group.ini

# E2：64 卡但 GPU 端口减半
./build/ChipletNetworkSim input/nvswitch_64card_half_gpu_ports.ini

# E3：64 卡 spine_leaf_links_per_pair=1
./build/ChipletNetworkSim input/nvswitch_64card_single_spine_link.ini
```

通过对比上述各配置的**饱和注入率/饱和吞吐**，判断哪一段缩小后对吞吐影响最大，即该段为瓶颈。

## 3. 方法三：在途包所在节点分布（已有）

`test_allreduce_diagnosis` 中的 **AtSwitch%**：在途包中位于 Switch 节点的占比。若 AtSwitch% 很高（如 97%），说明拥塞主要体现在**交换机缓冲区**，与「链路阻塞」统计结合可知：瓶颈在交换机**出端口**（本诊断进一步细化为 Leaf→GPU 等类型）。

---

## 4. 综合流程建议

1. 运行 **test_link_bottleneck_diagnosis**，得到各链路类型 blocked 占比。
2. 若某类型占比显著最高（如 Leaf→GPU），则**该段为当前瓶颈**。
3. 可选：做 **E1–E4** 分段隔离实验，验证改变该段容量后饱和吞吐是否敏感。
4. 优化方向：针对瓶颈段加大带宽（如 Leaf→GPU 对应更多链路或更大 buffer）、或改路由/流量分布以减轻该段争用。
