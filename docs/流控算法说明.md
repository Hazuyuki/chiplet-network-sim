# 流控算法说明

## 一、当前代码中的流控（Buffer-based / 接收端预留）

当前实现是**基于接收端 buffer 的流控**，等价于“发送前向接收端申请空间”：

1. **接收端状态**  
   每个输入 buffer（`Buffer`）维护 `vc_buffer_[vcb]`：该 VC 上**剩余可用的 flit 数**（单位 flit），初始为 `buffer_size`。

2. **发送条件（VC 分配阶段）**  
   在 `System::vc_allocate()` 中，对每个候选下一跳 VC 调用**下游 buffer** 的：
   - `allocate_buffer(vcb, p.length_)`  
   即：直接在下游 buffer 上做“预留”：若 `vc_buffer_[vcb] >= p.length_`，则原子减掉 `p.length_`，分配成功才能选该 VC。

3. **发送时**  
   - 同时要拿到**物理链路**：`allocate_sw_link()`、`allocate_in_link()`。  
   - 成功后把 packet 推到下游 buffer 的队列（`push_pkt`）。

4. **释放时机**  
   当 packet 的**尾 flit 离开**某个 buffer 时，在该 buffer 上调用：
   - `release_buffer(vcb, p.length_)`  
   即：把之前预留的 `p.length_` 加回该 buffer 的 `vc_buffer_[vcb]`。

**特点**：  
- 没有单独的“credit”报文；  
- 流控信息 = 下游 buffer 的剩余空间，在**发送时刻**由发送端“查一次”下游（allocate_buffer）；  
- 等价于“接收端预留 + 同步查询”，不是典型的“发送端持有一份 credit、接收端通过 credit 回报回填”的模型。

## 二、NVL72 / NVSwitch 的 Credit-based 流控

NVSwitch 内部通常使用**基于 credit 的流控**：

1. **发送端**  
   对每条“出边”（输出端口）× VC，维护一个 **credit 计数**：  
   - 表示“还可以向下游发送多少 flit（或多少单位）”。

2. **初始化**  
   - 每个 (输出端口, VC) 的 credit = 下游对应 VC 的 buffer 深度（如 `buffer_size`）。

3. **发送规则**  
   - 只有 `credit >= p.length_`（或按 flit 递减）时才允许发送；  
   - 发送时在**发送端**扣减 credit（例如 `credit -= p.length_`）。

4. **Credit 回报**  
   - 当**接收端**从该 VC 的 buffer 中“消费”掉数据（例如整包离开或按 flit 消费）时，向发送端回传 credit（或在本仿真里直接增加发送端对应 credit）；  
   - 可建模 credit 回报延迟（RTT）。

这样，流控状态主要在**发送端**的 credit 上，接收端通过“回报”更新发送端的 credit，更贴近 NVSwitch 的硬件实现。

## 三、如何改成基于 Credit 的流控

### 3.1 思路对比

| 项目           | 当前（Buffer-based）           | Credit-based（目标）                    |
|----------------|--------------------------------|----------------------------------------|
| 谁存“可发多少” | 接收端 `vc_buffer_[vcb]`       | 发送端 credit 计数                     |
| 发送条件       | 下游 `allocate_buffer()` 成功  | 发送端 credit ≥ 包长                   |
| 发送时         | 下游 buffer 减 `vc_buffer_`    | 发送端 credit 减 `p.length_`           |
| 释放时         | 下游 `release_buffer()`        | 下游消费后向**发送端**回报 credit      |

### 3.2 实现要点

1. **Node 上维护 credit**  
   - 对每个**输出端口**（对应一条链路到一个下游 buffer）、每个 VC，维护一个 credit 计数。  
   - 即：`credits_[port][vcb]`，初始值 = 下游该 VC 的 `buffer_size`（与当前配置一致）。

2. **Buffer 知道“上游”**  
   - 每个 `Buffer` 需要知道“谁在给我发”：上游 `Node*` 和上游的**出端口号**。  
   - 这样在“释放/消费”时，可以对该上游节点的对应 (port, vcb) **增加 credit**（即 credit 回报）。

3. **VC 分配（vc_allocate）**  
   - 不再对下游做 `allocate_buffer()`；  
   - 改为：  
     - 确定当前节点（发送端）和其出端口（指向候选 `vc.buffer` 的那个 port）；  
     - 检查该 (port, vcb) 的 **credit ≥ p.length_**；  
     - 满足则可选该 VC（后续在真正发送时再扣 credit）。

4. **真正发送时（allocate_in_link / 推包）**  
   - 在把包推入下游 buffer 时，在**发送端**对该 (port, vcb) 执行 **credit -= p.length_**。

5. **下游释放时（release_buffer）**  
   - 当 packet 尾 flit 离开该 buffer 时，不再（或不仅）更新下游 `vc_buffer_`；  
   - 调用**上游节点**的“回报 credit”：  
     `upstream_node->return_credit(upstream_port, vcb, p.length_)`。

6. **拓扑构建**  
   - 在拓扑连接好所有 `link_buffers_` 后，对每个 buffer 设置其 `upstream_node` 和 `upstream_port`（即：哪个 Node 的哪个 port 连到该 buffer）。

7. **配置项**  
   - 增加配置（如 `flow_control = buffer | credit`），在 VC 分配与释放路径根据配置走“当前 buffer 预留”或“credit 检查/扣减/回报”。

按上述修改后，流控语义就变为“发送端持 credit、接收端消费后回报”的 **credit-based** 模型，可与 NVL72/NVSwitch 的 credit 流控对应起来；若需要更贴近硬件，再在回报路径上加 credit 延迟即可。
