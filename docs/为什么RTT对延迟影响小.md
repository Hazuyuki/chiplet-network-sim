# 为什么 Credit Return Delay (RTT) 对「延迟」影响很小？

## 一、RTT 到底影响什么？

**Credit return delay** 模拟的是：接收端在“包尾离开 buffer”后，**过多少周期**才把 credit 还到发送端。

- **不改变**：已经发出去了的包的路径、链路延迟、跳数。
- **只改变**：发送端**下一次**能再发一包的时间——credit 回来得越晚，发送端越晚才能再占用这条 (port, VC)。

所以：

- **单包延迟** = 跳数 × 链路延迟 + 排队。  
  包一旦被发出，其延迟就和“credit 何时回报”无关，只和当时网络里的排队有关。
- **RTT 影响的是**：发送端还能不能持续往这条链路上发、能维持多高的**注入率/吞吐**，而不是“这一包要飞多久”。

因此：**RTT 主要影响吞吐和饱和点，对「平均延迟」曲线影响本来就不大。**

---

## 二、为什么图上「延迟 vs 注入率」几乎重合？

1. **低注入**  
   注入率不高时，credit 够用，包几乎不等 credit。延迟 ≈ 最小路径延迟（如 6 cycle），和 RTT=0 或 8 关系都不大。

2. **高注入**  
   - 延迟主要来自**排队**：前面有包占着 VC/链路，后面的包就要等。
   - RTT 大 → 发送端更早“没 credit” → 实际注入被压得更低 → 在途包更少 → 排队可能反而**更短**。
   - 所以同一「请求注入率」下，RTT 大时，到达的包经历的排队可能更少，**平均延迟**不一定更高，有时甚至略低。

3. **我们画的是「请求注入率」**  
   横轴是“设定”的注入率；RTT 大时，实际被网络接受的注入会少一些（更多包在源端等 credit）。  
   若画的是「实际接收率」或「饱和吞吐」随 RTT 的变化，RTT 的影响会明显得多。

**结论**：  
RTT **本来就不该**明显拉高「平均包延迟」；它主要是让**可维持的吞吐**和**饱和注入率**随 RTT 增大而下降。要看 RTT 的影响，应看**吞吐 / 饱和注入率 / 超时数**随 RTT 的变化。

---

## 三、怎样在实验里看到 RTT 的影响？

1. **画「接收率 (throughput) vs 注入率」**  
   同一注入率下，RTT 越大，接收率往往略低；饱和点（曲线拐平）会左移。

2. **画「饱和注入率 vs RTT」**  
   定义饱和（如延迟 > 某阈值或接收率不再随注入率上升），看饱和注入率随 `credit_return_delay` 增大是否下降。

3. **看超时数**  
   高注入、大 RTT 时，发送端更容易长期缺 credit，超时包数可能更多。
