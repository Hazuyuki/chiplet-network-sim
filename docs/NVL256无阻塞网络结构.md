# NVL256 无阻塞网络结构

## 1. 背景与参考

NVIDIA 未公开「NVL256」的正式规格，但可根据 **NVL72** 与 **NVSwitch** 技术文档推断 256-GPU 无阻塞网络的典型结构。

### 1.1 NVL72 参考结构（公开信息）

- **18× Compute trays**：每 tray 4 GPU → 共 72 GPU
- **9× NVLink switch trays**：形成 spine，提供 57.6 Tbps 全双工带宽
- **互联方式**：Access NVLinks（GPU↔Switch）+ Trunk NVLinks（Switch↔Switch）
- **Compute : Switch 比例**：2 : 1（2 个 compute tray 对应 1 个 switch tray）

### 1.2 NVSwitch 芯片特性

- **18 端口**、内部 **18×18 全连接 crossbar**（无阻塞）
- 单端口 50 GB/s，合计约 900 GB/s
- 任意端口可同时与任意其他端口通信，无内部阻塞

---

## 2. NVL256 无阻塞拓扑推断

按 NVL72 的 2:1 比例缩放至 256 GPU：

| 参数 | NVL72 | NVL256 |
|------|-------|--------|
| GPU 总数 | 72 | 256 |
| Compute tray 数 | 18 | 64 |
| GPU / tray | 4 | 4 |
| Switch tray 数 | 9 | **32** |
| Compute : Switch | 2 : 1 | 2 : 1 |

等效为本仿真中的「group」抽象：

- **32 groups × 8 GPU/group = 256 GPU**
- 每组 4 个 leaf NVSwitch
- **32 个 spine switch tray** → 在本模型中 spine 数量取 `max_gpu_ports` 以保证无阻塞

---

## 3. 无阻塞条件

### 3.1 Leaf-Spine 无阻塞

- 每个 leaf 有 `max_gpu_ports` 条上行到 spine（例如 8 GPU×5 links = 40）
- spine 数量 = `max_gpu_ports`，每个 leaf 的上行一一对应到不同 spine
- 任一 leaf 上行带宽 = spine 下行带宽，**无 oversubscription**

### 3.2 配置要点

```
spine_non_blocking = true   # 自动设置 num_spine_switches = max_gpu_ports
spine_leaf_links_per_pair = 1  # 每对 (leaf, spine) 的链路数；>1 时为 NVL256 式多链路无阻塞
num_groups = 32             # 256 GPU 时
num_gpus_per_group = 8
num_switches_per_group = 4
gpu_nvlink_ports = 18
```

- **spine_leaf_links_per_pair**（默认 1）：同一 (leaf, spine) 之间的并行链路数。设为 2、4 等可提高 spine–leaf 段带宽，进一步减轻该段出端口争用，形成更强的无阻塞能力。需配合 `routing_algorithm = min` 使流量摊到多链路上。

### 3.3 与阻塞的关系

- **拓扑无阻塞**：bisection 带宽足够，leaf-spine 无 oversubscription
- **流控与调度仍会引入阻塞**：多流争用、credit 回报延迟、switch 输出口争用等

## 4. 本仿真中的实现

### 4.1 配置

- **64 GPU**：`input/nvswitch_allreduce.ini`（8 group × 8 GPU）
- **256 GPU**：`input/nvswitch_nvl256.ini`（32 group × 8 GPU）

两者均使用 `spine_non_blocking = true`，spine 数量自动为 `max_gpu_ports`，满足 leaf-spine 无阻塞。

### 4.2 减少阻塞的配置建议

拓扑无阻塞只保证 bisection 带宽；流控和调度仍会引入阻塞。可尝试：

- `buffer_size` 128–256：增大 credit 池，减轻反压
- `credit_return_delay` 0–2：缩短 RTT，加快 credit 回流
- `routing_algorithm = min`：包泼洒，充分利用多路径

### 4.3 阻塞来源说明

诊断表明 all-reduce 饱和 ~4.2 的主因是：多流争用、流控反压、ring 流量模式，而非 bisection 带宽不足。拓扑无阻塞可保证单流达 18。

## 5. 为何受限于「出链路带宽」？NVL256 为何不易出现？

### 5.1 仿真里的「出链路」模型

- 本仿真对**每条物理链路**建模为：每周期最多 1 flit（`allocate_in_link` / credit 流控）。
- 交换机**内部**：每个输入端口可竞争任意出端口，不同出端口可同时各走 1 个包，等价于 **crossbar 无阻塞**（多出端口并行）。
- 因此瓶颈不在「交换机内部」，而在**多条流争抢同一条出链路**：当多个包要从同一交换机发往同一下一跳时，该下一跳的输入 buffer 每周期只能收 1 个 → 其余在交换机内排队 → 表现为「受限于出链路带宽」。

### 5.2 真实 NVL256 / NVSwitch 的路由与结构

- **单芯片 NVSwitch**：内部 **18×18 全连接、无阻塞 crossbar**，18 个端口可同时以线速互传；与仿真一致，单芯片内部无出端口争用。
- **NVL256 拓扑**：Leaf–Spine 两级无阻塞胖树；每个 leaf 有大量上行到 spine（如 `max_gpu_ports` 条），spine 数量与之匹配，bisection 无 oversubscription。
- **路由与负载均衡**：
  - Fabric Manager 等对 NVSwitch 做路由与资源管理，便于在 fabric 上合理分布流量。
  - **NCCL**：根据拓扑做图搜索，自动构建「最合适的 ring / tree」，而不是固定一条全局 ring；对 NVLink/NVSwitch 系统会做拓扑感知的 all-reduce（含 ring 与 tree 等），使流量更贴合 fat tree 的带宽分布。

### 5.3 为何 NVL256 不易遇到「出链路」瓶颈

| 方面 | 本仿真（当前） | 典型 NVL256 实践 |
|------|----------------|------------------|
| **拓扑 / 无阻塞** | 已满足 leaf–spine 无阻塞 | 同左，bisection 充足 |
| **交换机内部** | 多出端口并行，等价无阻塞 | 18×18 crossbar 无阻塞 |
| **流量模式** | 固定 **全局 ring** (i→(i+1)%N) | NCCL **拓扑感知** ring/tree，常为分层或与拓扑对齐 |
| **路由粒度** | **包级** 选路（min 路由泼洒到多候选，但单包路径固定） | 可配合 **流级/流片级** 负载均衡与自适应路由 |
| **集体算法** | 单一 ring all-reduce | 多算法与拓扑匹配，减少跨层、跨 spine 热点 |

要点：

1. **出链路瓶颈在仿真里是正确建模**：每条链路 1 flit/cycle，多流争同一下一跳就会排队；真实硬件同样受「每条链路线速」限制。
2. **NVL256 不易踩中的原因**主要是**流量形态与算法**：
   - 使用**拓扑感知的 ring/tree**，减少大量流同时争抢同一 spine 或同一组出链路；
   - 分层或按 group 的 all-reduce 能更好利用 leaf–spine 的多路径，避免像「全局单 ring」那样在少数链路上形成热点。
3. 若在仿真中希望更接近 NVL256 行为，可考虑：**拓扑感知的 ring**（如先组内 ring 再组间）、**多 ring 或 tree**，以及更多 VC/更大 buffer 等，以降低对单条出链路的争用。
