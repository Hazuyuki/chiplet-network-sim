# 高 R 时 Throughput 反而上升的根源分析

## 现象

RTT 实验里，取每个 R 下「所有注入率对应的 max(throughput)」画图时，会出现 **R 增大（如 R=24）时吞吐反而比 R=20 更高**（例如 9.88 vs 9.10），与公式「R 越大、吞吐应单调下降」不符。

## 根源（三个叠加因素）

### 1. 测量窗口长度不一致（最主要）

每个 (R, 注入率) 的测量阶段是：

```cpp
for (i = 0; i < simulation_time && TM->message_timeout_ <= timeout_limit; i++) {
  TM->genMes(all_packets);
  run_one_cycle(all_packets, network, i);
}
TM->print_statistics();  // 写入 CSV：injection_rate, latency, receiving_rate
```

- 循环会在 **达到 50 个超时** 时提前结束，不会跑满 `simulation_time`（如 800）个周期。
- 因此：**不同 (R, 注入率) 实际跑到的周期数不同**：
  - 高 R + 高注入：容易很快触发 50 次超时 → 测量窗口很短（例如一两百周期）。
  - 低 R 或低注入：可能跑满 800 周期 → 测量窗口长。

吞吐公式是：

```text
receiving_rate = injection_rate × (message_arrived / all_message_num_)
```

即「注入率 × 送达比例」，而 `message_arrived` 和 `all_message_num_` 都是在**当前这次实际跑到的周期数**内累加的。因此：

- **窗口短**：平均是在「很少周期」上算出来的，方差大，容易出现偶然偏高或偏低的点。
- **窗口长**：平均更稳定，但不同 R 下「何时因超时提前结束」不同，所以**不同 R 之间并不是在「相同测量长度」下比吞吐**。

所以：**R=24 的某个点**（例如注入 15.5）可能恰好在一个「较短但运气好」的窗口里得到 9.88，而 **R=20 的某个点**（例如注入 15）在另一个长度的窗口里得到 9.10。两者不是「同一条件、只改 R」的对比，而是**不同测量长度 + 不同注入率**下的两个样本，出现 R 大反而吞吐高是可能的。

### 2. 「max」对应的注入率随 R 变化

- 对 **R=20**：所有注入率里，**max(throughput)** 出现在 **injection=15**（9.10）。
- 对 **R=24**：**max(throughput)** 出现在 **injection=15.5**（9.88）。

也就是说，我们画图时比较的是：

- R=20：在「注入率=15 时」的那次运行得到的吞吐；
- R=24：在「注入率=15.5 时」的那次运行得到的吞吐。

这是**两个不同的工作点**（不同注入率、不同运行长度、不同超时行为），而不是「同一注入率、只改 R」的对照。因此即使用同一公式，**取 max 后随 R 单调**的假设也不成立，出现 R 增大后 max 反而略升是数据与取法导致的，不是公式错。

### 3. 方差与饱和区波动

在饱和区附近：

- 送达比例 `message_arrived / all_message_num_` 对「何时触发超时、跑了多少周期」很敏感；
- 不同 R 下 credit 回报节奏、排队长度不同，短窗口内的「瞬时吞吐」会有波动。

所以 9.88 与 9.10 的差异里，有一部分是**同一 R 下多次跑也会出现的方差**，不全是「R 增大导致容量增大」的真实效应。

---

## 小结

| 因素 | 说明 |
|------|------|
| 测量长度不一致 | 因 50 次超时提前结束，每个 (R, 注入率) 的实际周期数不同，吞吐是在不同长度窗口上算的平均，不可直接比。 |
| max 来自不同注入率 | 每个 R 的 max(throughput) 取自不同注入率（如 15 vs 15.5），相当于不同工作点，不满足「只改 R」的对照。 |
| 饱和区方差 | 短窗口 + 饱和区波动，使单次运行的吞吐有随机性，可能偶然出现 R 大时略高。 |

因此：**throughput 在高 R 反而增长，是「测量方式 + 取 max 方式」带来的现象，不是仿真或公式在说 R 越大容量越大**。要得到随 R 单调下降、且物理意义清晰的曲线，需要从实验设计上对齐测量条件（见下）。

## 可选改进（实验设计）

1. **固定测量窗口**  
   每个注入率都跑满 `simulation_time` 个周期再算吞吐（或固定一个周期数），不因超时提前结束而缩短窗口；或记录实际周期数，用 `message_arrived / cycles_run` 作为吞吐，使不同 (R, 注入率) 在「同一时间基准」上可比。

2. **固定注入率再比 R**  
   对所有 R 都画「注入率 = 18（或同一值）时的 throughput」，这样是「同一 offered load、不同 R」的对比，曲线会随 R 单调下降，且饱和吞吐的定义一致。

3. **取 max 时做单调约束**  
   若仍用每个 R 的 max(throughput)，可在绘图时对 R 做单调不增后处理（例如 running minimum），避免图上看成「R 越大容量越大」，仅作展示用；真实因果仍以固定测量窗口或固定注入率的对比为准。
